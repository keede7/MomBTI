# 리포트 생성 방식: 규칙 기반 vs 규칙 기반 + Claude API

## 결론
**1차 MVP는 규칙 기반으로 만든다.** 조언 문장 생성부는 `AdviceNarrator` 인터페이스로 분리해서, 2차에 Claude 구현체를 끼워 넣을 수 있게 한다 (ADR-002).

## 핵심 차이
두 방식 모두 **수치(BMR, TDEE, 체중 변화 곡선, 목표 도달일)는 코드에 넣은 공식으로 계산한다.** LLM에게 숫자를 계산시키면 정확성을 보장할 수 없기 때문이다. 하이브리드에서도 Claude는 이미 계산된 숫자를 **설명하고 개인화하는 역할**만 맡는다.
그래서 차이는 "숫자가 맞느냐"보다 아래 두 가지에서 난다.
- **조언이 얼마나 개인에게 맞춰지느냐**
- **그 대가**: 정확성 리스크, 비용, 테스트 난이도

## 요구사항별 비교
| 요구사항 | 규칙 기반만 | 규칙 기반 + Claude API |
|---|---|---|
| 1. 수치화된 변화 그래프 | ✅ Hall(2011) 동적 체중모델로 주차별 체중·체지방 계산 | ✅ 같음 (그래프는 규칙 엔진이 그림) |
| 2. 목표 체형 도달 시점 | ✅ 시뮬레이션으로 "약 N주 뒤 목표 체중" 계산 | ✅ 같음 + "왜 이 기간인지"를 자연스러운 문장으로 설명 |
| 3. 논문 수준 근거 | ✅ **가장 강함.** 숫자·조언마다 공식과 논문이 1:1로 연결되고, 결과가 항상 같으며 TDD로 검증 가능 | ⚠️ 숫자는 같지만 **문장에 없는 수치나 가짜 논문이 섞일 위험**이 있음. 고정 참고문헌 목록, 계산값만 인용, 응답 검증 같은 안전장치가 필요 |
| 4. 추가 정보 입력 유도 | 🔶 구조화된 선택지(활동량, 목표, 체지방률 등)는 잘 처리함. **자유 텍스트는 거의 활용하지 못함** (키워드 매칭 수준) | ✅ **가장 큰 장점.** "야근이 많고 무릎이 안 좋아요, 회식이 잦아요" 같은 글을 해석해 조언에 반영 |
| 5. 식단·운동 제안 | 🔶 단백질 1.6g/kg(Leidy 2015), 칼로리 구간별 식단 템플릿. 정확하지만 **템플릿이라 다소 획일적** | ✅ 한식 선호, 알레르기, 생활 패턴에 맞춘 식단. 다만 **LLM이 만든 메뉴의 칼로리 합계는 부정확할 수 있어** 서버에서 다시 검증해야 함 |
| 6. 주 4일/5일 수행 시 결과 | ✅ 빈도별 운동 소비열량(2024 Compendium of Physical Activities)을 넣어 각각 시뮬레이션 | ✅ 같음 (계산은 규칙 엔진) |

## 그 외 비교
| 항목 | 규칙 기반 | + Claude API |
|---|---|---|
| 결과 재현성 | 같은 입력이면 항상 같은 결과 | 문장이 매번 조금씩 달라짐 |
| 테스트 (TDD 규칙) | 전부 단위 테스트 가능 | LLM 부분은 모킹해야 하고 품질 검증이 어려움 |
| 응답 속도 | 즉시 (ms 단위) | 수 초~10초 이상 추가 |
| 비용·운영 | 없음 | API 키, 요청당 비용, 장애 시 대체 로직 필요 |
| 개인화 수준 | 중간 | 높음 |
| 개인정보 | 외부 전송 없음 | 건강 정보가 외부 API로 전송됨 (동의, 처리방침 필요) |

## 2차 확장 경로 (하이브리드로 갈 때)
1. `AdviceNarrator`의 Claude 구현체를 추가한다. 입력은 계산이 끝난 `Report`와 사용자 자유 텍스트다.
2. 계약은 하나다. **LLM은 숫자를 만들거나 바꾸지 않는다.** 응답에 나온 숫자가 `Report`에 없는 값이면 버리고 템플릿 문장으로 대체한다.
3. 인용은 `Evidence` enum 목록에서만 고르게 한다. 목록 밖 인용은 제거한다.
4. LLM이 제안한 식단은 서버가 칼로리와 탄단지를 다시 계산해 검증하고, 목표 대비 ±5%를 넘으면 템플릿으로 대체한다.
5. 타임아웃과 장애 시에는 `TemplateAdviceNarrator`로 대체한다 (리포트는 항상 나온다).
6. 외부 전송 동의 UI와 개인정보 처리방침을 추가한다 (ADR-003 재검토).
