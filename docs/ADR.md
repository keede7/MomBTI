# Architecture Decision Records

## 철학
다이어트의 길(얼마나 먹어야 하는지)과 그 결과 예측만 명확하게 보여준다.
근거 없는 숫자는 출력하지 않는다. 최소 입력으로도 완전한 결과를 낸다.
우선순위는 안전 > 정확성 > 개인화. MVP는 작동하는 최소 구현을 선택한다.

---

### ADR-001: Thymeleaf SSR + Chart.js
**결정**: Spring Boot 안에서 Thymeleaf로 화면을 렌더하고, 그래프만 Chart.js(cdnjs)로 그린다.
**이유**: 빌드가 하나라 단순하다. 서버가 계산한 값을 그대로 렌더하므로 계산과 화면이 어긋나지 않는다.
**트레이드오프**: SPA 수준의 부드러운 상호작용을 포기한다. 재검토: 계정, 공유, 부분 갱신이 필요해질 때.

### ADR-002: 규칙 기반 엔진 + AdviceNarrator 확장점
**결정**: 모든 수치와 조언을 논문 공식과 규칙으로 만든다. 문장 생성부는 `AdviceNarrator` 인터페이스로 분리한다.
**이유**: 결과가 재현되고, TDD로 검증할 수 있고, 숫자마다 출처를 연결할 수 있다. 비교 내용은 docs/REPORT_STRATEGY.md.
**트레이드오프**: 자유 텍스트 해석과 깊은 개인화를 포기한다. 재검토: 2차에 Claude 구현체를 연결할 때.

### ADR-003: 서버 무저장, 입력값 무로깅
**결정**: 입력값과 결과를 저장하지 않고, 로그와 예외 메시지에도 남기지 않는다.
**이유**: 건강 정보는 개인정보보호법상 민감정보다. 저장하지 않으면 유출 위험이 없다.
**트레이드오프**: 다시 보기, 공유, 사용 통계를 포기한다.

### ADR-004: Hall 동적 체중모델 단순화 채택
**결정**: 하루 단위 에너지 밸런스 + Forbes 분배 + 체중에 따른 BMR 재계산으로 예측한다. "7,700kcal = 1kg" 정적 규칙은 쓰지 않는다.
**이유**: 정적 규칙은 장기 감량을 크게 과대평가한다 (Hall 2011).
**트레이드오프**: 구현과 테스트가 복잡해지고, 다른 계산기보다 결과가 느리게 나와 보인다 (FAQ로 설명).

### ADR-005: BMR은 Mifflin-St Jeor 기본, 체지방률이 있으면 Cunningham(Katch-McArdle)
**결정**: 체지방률 미입력 시 Mifflin-St Jeor, 입력 시 제지방량 기반 Cunningham 1991 식(370 + 21.6 × 제지방량, 흔히 Katch-McArdle로 불림)을 쓴다. 원문 대조 결과 이 식의 원 출처는 Cunningham 1991이다.
**이유**: Mifflin-St Jeor가 일반 성인에서 가장 정확한 편이다 (Frankenfield 2005). 제지방량을 알면 체형 차이를 더 잘 반영한다.
**트레이드오프**: 극단적인 체형에서는 두 공식 모두 오차가 크다 (개인차 밴드로 표현).

### ADR-006: KSSO 2022 아시아 BMI 기준
**결정**: BMI 구간은 대한비만학회 2022 기준(23 / 25 / 30)을 쓴다.
**이유**: 한국 사용자 대상이다.
**트레이드오프**: 서구 기준(25 / 30)과 결과가 다르다.

### ADR-007: 필수 입력은 성별·나이·키·몸무게 4개
**결정**: 사용자가 처음 생각한 3개(성별, 키, 몸무게)에 나이를 더해 필수로 받는다.
**이유**: 나이는 BMR 공식에 꼭 필요하고, 미성년자를 가려내는 데도 쓴다.
**트레이드오프**: 입력이 하나 늘어난다 ("기초대사량 계산에 필요해요" 안내로 보완).

### ADR-008: 선택 항목은 근거 있는 기본값으로 대체하고 "추정"으로 표시
**결정**: 선택 항목이 비면 PRD의 기본값 표대로 채운다. 기본값 적용은 `ProfileDefaults`에서만 한다.
**이유**: 최소 입력으로도 빈 곳 없는 리포트를 주기 위해서다.
**트레이드오프**: 개인 오차가 커진다. 개인차 밴드와 "더 정확하게 보기"로 보완한다.

### ADR-009: 건강 확인 질문을 받지 않음 (사용자 결정)
**결정**: 임신·수유, 질환, 섭식장애 이력을 묻지 않는다.
**이유**: 건강이 좋지 않은 사람은 다이어트를 계획하지 않는다고 보고, 입력 마찰을 줄인다.
**트레이드오프**: 위험군을 걸러내지 못한다. 상단 안전 안내 한 줄, 입력값 기반 안전 규칙(ADR-010), 면책으로 최소한 대응한다. 재검토: 서비스 공개 범위가 넓어질 때.

### ADR-010: 입력값 기반 안전 규칙
**결정**: 19~80세만 계산한다. 19세 미만은 안내 화면으로 보낸다. BMI 18.5 미만은 감량하지 않는다. 목표 BMI는 18.5 이상이어야 한다. 섭취 하한은 여 1,200 / 남 1,500kcal다 (AHA/ACC/TOS 2013 처방 범위 하단). 적자 상한은 min(소비량 25%, 주당 체중 1%)이고, 65세 이상은 20%다. 체중 1%를 kcal로 바꿀 때는 7,700kcal/kg이 아니라 시작 시점 Forbes 분배로 구한 에너지 밀도를 쓴다 (ADR-004와 일관).
**이유**: 추가 질문 없이 입력값만으로 지킬 수 있는 최소 안전선이다.
**트레이드오프**: 빠른 감량을 원하는 사용자에게는 결과가 느리게 보인다.

### ADR-011: 활동량은 운동을 제외한 일상 활동으로 정의
**결정**: 활동량 단계는 직업과 이동만 반영하고, 운동은 시나리오에서만 더한다.
**이유**: 둘 다 운동을 포함하면 소비량을 이중으로 계산한다.
**트레이드오프**: 사용자가 "운동 제외"를 이해하도록 문구와 예시가 필요하다.

### ADR-012: 하루 단위 계산 52주, 표시는 최대 26주
**결정**: 시뮬레이션은 하루 단위로 52주까지 하고, 그래프는 최대 26주까지만 보여준다. 섭취량은 시작 시점 값으로 고정한다.
**이유**: 52주까지 계산해야 "도달 불가"와 평형 체중을 판단할 수 있다. 표시는 동기 부여에 맞춘다 (ADR-021).
**트레이드오프**: 실제로 식단을 재조정하는 상황은 반영하지 않는다 ("4주마다 다시 계산" 안내).

### ADR-013: 불확실성 밴드와 범위 표기
**결정**: BMR ±10%로 따로 시뮬레이션해 밴드와 도달 주차 범위("18~23주")를 보여준다.
**이유**: 공식 자체의 오차를 숨기면 과신을 부른다.
**트레이드오프**: 결과가 덜 단정적으로 보인다.

### ADR-014: 표가 기본이고 차트는 점진적 향상
**결정**: 서버가 같은 데이터의 표를 항상 렌더하고, 차트는 JS로 덧붙인다.
**이유**: CDN 장애, JS 비활성, 스크린리더 환경에서도 정보를 잃지 않는다.
**트레이드오프**: 같은 데이터를 두 번 렌더한다.

### ADR-015: 도메인은 순수 Java
**결정**: 계산과 규칙 계층은 Spring에 의존하지 않는다.
**이유**: 단위 테스트가 빠르고 프레임워크에서 독립적이다.
**트레이드오프**: Bean 등록 설정(`DomainBeanConfig`)이 따로 필요하다.

### ADR-016: 성별은 남/여 이진
**결정**: 계산용 성별은 남/여만 받는다.
**이유**: 사용하는 공식의 계수가 이진으로만 정의되어 있다.
**트레이드오프**: 포용성에 한계가 있다. "계산 공식에 쓰는 생물학적 성별"로 이유를 안내한다.

### ADR-017: POST 결과를 직접 렌더 (PRG 미사용)
**결정**: POST /report와 /report/refine은 리다이렉트 없이 리포트를 바로 렌더한다.
**이유**: 저장하지 않으므로 리다이렉트할 대상이 없다.
**트레이드오프**: 새로고침하면 브라우저의 재전송 확인이 뜬다. CSRF는 상태 변경이 없어 적용하지 않는다.

### ADR-018: 현실 보정(80%) 라인은 가정으로 표시
**결정**: "계획의 80%만 지킨 경우" 라인을 토글로 제공하고 "가정"이라고 적는다.
**이유**: 실제로 계획을 100% 지키기는 어렵다.
**트레이드오프**: 80%라는 숫자의 근거가 약해서 기본 표시에서는 뺀다.

### ADR-019: 운동 루틴을 제공하지 않음 (사용자 결정)
**결정**: 주간 운동 계획, 운동 목록, 세트·시간 안내를 만들지 않는다.
**이유**: 사람마다 운동 강도와 강도를 느끼는 정도가 달라서, 일괄 루틴은 맞지 않는다.
**트레이드오프**: 운동 안내 기능을 포기한다 (docs/BACKLOG.md).

### ADR-020: 운동은 빈도별 결과만 비교하고, 1회는 "중강도 45분"으로 가정
**결정**: 식단만 / 주 3·4·5일 운동의 결과를 비교한다. 운동 1회는 MET 4.8(2024 Compendium 코드 17200, 빠르게 걷기) × 45분으로 계산한다.
**이유**: 처음 요구사항 6(주 4일·5일 수행 시 결과)을 루틴 없이도 지킬 수 있다. MET 값은 최신판을 우선한다 (2011판 4.3 → 2024판 4.8).
**트레이드오프**: 개인 강도가 반영되지 않는다. 범례, 표, FAQ에 가정을 명시한다.

### ADR-021: 그래프 기본 12주(2주 간격) + 6개월 토글
**결정**: 그래프는 기본 12주를 2주 간격으로 보여준다. 목표가 12주 밖이면 "6개월까지 보기" 토글을 준다.
**이유**:
- 짧은 축에서는 초반 변화가 크게 보여서 동기 부여에 유리하다.
- 2주 간격이면 하루하루의 체중 변동이 평균으로 묻힌다.
- 목표가 그래프 밖에 있으면 막막하므로 6개월 보기로 이어 준다.

**트레이드오프**: 장기 전망을 보려면 한 번 더 눌러야 한다.

### ADR-022: 선택 입력은 3개로 제한
**결정**: 선택 입력은 활동량, 목표 체중, 체지방률만 받는다.
**이유**: 추가 입력이 필수처럼 느껴지지 않게 하고, 예측에 가장 큰 영향을 주는 항목만 남긴다.
**트레이드오프**: 수면, 식습관 등에 따른 개인화를 포기한다 (docs/BACKLOG.md).

### ADR-023: 개선할 부분은 리포트 하단에 배치
**결정**: 개선할 부분을 근거 바로 위로 내리고, 요약 카드에서도 뺀다.
**이유**: 핵심은 길(섭취 목표)과 예측이다.
**트레이드오프**: 개선점을 보는 사용자가 줄어든다.

### ADR-024: 복부 지표 제외
**결정**: 허리둘레 입력과 허리-키 비율을 만들지 않는다.
**이유**: 다이어트의 길과 예측이라는 목표와 직접 관련이 적다.
**트레이드오프**: 복부 비만 위험 안내를 포기한다.

### ADR-025: 목표 날짜 제외
**결정**: 목표 날짜 입력과 실현 가능성 판정을 만들지 않는다.
**이유**: 특정 날짜에 맞춘 조언이 아니라 변화 예측이 목적이다.
**트레이드오프**: "결혼식까지 가능한가?" 같은 질문에 답하지 못한다.

### ADR-026: 재계산은 같은 페이지를 새 결과로 교체
**결정**: "더 정확하게 보기"로 재계산하면 리포트 전체를 새 결과로 바꾼다. 전후 비교는 하지 않는다.
**이유**: MVP 범위를 줄인다.
**트레이드오프**: 무엇이 바뀌었는지 사용자가 기억해야 한다 (전후 비교 제안은 docs/BACKLOG.md).
